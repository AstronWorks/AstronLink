# VPN 모드 (가상 네트워크 어댑터)

클라이언트가 **가상 네트워크 어댑터(TUN)** 를 만들고, 애플리케이션 트래픽이 프록시 설정(SOCKS5 / `HTTPS_PROXY`) 없이 그 어댑터를 통해 서버로 흐르게 하는 모드입니다.

- **최초 핸드셰이크는 기존(물리) 네트워크**로 진행합니다. 서버 → 클라이언트 TLS 다이얼, TOFU 지문 확인, `ClientRegister`/`RegisterResp` 교환은 지금과 동일합니다.
- 핸드셰이크가 끝나면 클라이언트가 VPN 세션을 요청하고, 서버가 내려준 주소로 어댑터를 올립니다. **이후 트래픽은 어댑터를 통해** 진행합니다.
- 기존 SOCKS5 / HTTP CONNECT / 포트 포워드 / 노출(expose) 터널은 그대로 동작하며 함께 쓸 수 있습니다.

## 구조

```
  CLIENT (NAT/방화벽 뒤)                                     SERVER (공인)
 ┌──────────────────────────────────┐                 ┌───────────────────────────────────┐
 │ 앱 (브라우저, curl, RDP ...)      │                 │                                   │
 │   │ OS 라우팅 (0/1, 128/1 또는     │                 │  per-client 유저스페이스 TCP/IP 스택 │
 │   ▼          vpn.routes)          │                 │  (gVisor netstack, 게이트웨이       │
 │ TUN 어댑터 10.77.0.2/24           │  MsgVPNPacket   │   10.77.0.1)                      │
 │   │  adapter.Manager ─────────────┼── (기존 TLS ───►│   ├─ TCP/UDP 종단 → 실제 목적지로    │
 │   ▲                               │    제어 연결)    │   │   다이얼 (SSRF 가드 적용)        │──► 인터넷
 │   └───────────────────────────────┼◄────────────────│   ├─ 10.77.0.1:53  → 서버 리졸버    │
 │                                   │                 │   └─ 10.77.0.1:<data_port>         │
 │ 서버 IP 는 bypass 라우트로         │                 │        → 터널 데이터 연결 처리       │
 │ 물리 NIC 유지 (제어 연결 루프 방지) │                 │                                   │
 └──────────────────────────────────┘                 └───────────────────────────────────┘
```

- **클라이언트(`internal/vpn/adapter`)**: TUN 어댑터 생성·주소/MTU 설정·라우트·DNS·bypass 라우트를 관리하고, 어댑터에서 읽은 IP 패킷을 활성 서버 세션으로 보냅니다. Linux는 `/dev/net/tun` + iproute2(`ip`), Windows는 Wintun + IP Helper API(winipcfg)를 사용합니다.
- **서버(`internal/vpn/netstack`)**: 제어 연결마다 독립된 유저스페이스 TCP/IP 스택을 띄웁니다. 클라이언트의 TCP/UDP 흐름을 종단하고 일반 소켓으로 실제 목적지에 다이얼합니다(출구 노드). **서버에는 TUN 장치도, 관리자/root 권한도, OS NAT 설정도 필요 없습니다.** Windows GUI 서버(`cmd/winserver`)에서도 동일하게 동작합니다.
- **공통(`internal/vpn`)**: 설정 검증과 협상 파라미터.

## 핸드셰이크 순서

```
SERVER                                              CLIENT
  │── TLS 1.3 다이얼 (물리 네트워크) ──────────────────►│
  │   TOFU 지문 확인                                  │
  │── MsgClientRegister ─────────────────────────────►│ 토큰 검증
  │◄──────────────────────────────── MsgRegisterResp ─│
  │◄─────────────── MsgRequestTunnel ... (기존과 동일) ─│
  │◄──────────────────────────── MsgVPNOpen{MTU} ─────│ (vpn.enabled 일 때)
  │  per-client netstack 생성                          │
  │── MsgVPNConfig{ClientAddr, Gateway, MTU, DNS, ───►│ 어댑터 생성/주소·라우트·DNS 적용
  │                DataPort}                          │ (서버 IP는 bypass 라우트)
  │◄═══════════════ MsgVPNPacket (양방향, raw IP) ═════►│ 이후 트래픽은 어댑터 경유
```

- `MsgVPNPacket` 은 Envelope.Payload 에 **IP 패킷 원본**을 그대로 싣습니다(내부 gob 인코딩 없음). 프레임의 길이 프리픽스와 본문은 한 번의 Write 로 전송되어 패킷당 TLS 레코드 1개입니다.
- 서버가 VPN 을 끈 경우 `MsgVPNConfig{Status:"error"}` 로 거절하고, 클라이언트는 어댑터 없이 기존 기능만으로 계속 동작합니다. VPN 을 모르는 구버전 서버는 응답하지 않으며 클라이언트가 10초 후 경고 로그를 남깁니다.

## 노출(expose) 터널의 데이터 연결도 어댑터 경유

VPN 이 활성인 세션에서는 `MsgOpenConnection` 에 대한 **데이터 다이얼백이 `게이트웨이:data_port`(예: `10.77.0.1:8444`)로 향해 어댑터를 통과**합니다. 서버 스택이 이 연결을 받아 데이터 연결 핸들러로 직접 넘기므로, 클라이언트에서 서버의 물리 `:8444` 로 나가는 아웃바운드 연결이 필요 없습니다. 게이트웨이에서 열려 있는 TCP 포트는 이 데이터 포트뿐이며(관리 API 등 서버의 다른 로컬 서비스는 노출되지 않음), 나머지 포트는 RST 로 거절됩니다.

## 라우팅과 bypass

| 항목 | 동작 |
|------|------|
| `vpn.routes` 비움 (기본) | 전체 터널. `0.0.0.0/0` 대신 `0.0.0.0/1` + `128.0.0.0/1` 을 어댑터에 설치해 **원래 기본 라우트를 건드리지 않습니다.** |
| `vpn.routes` 지정 | 지정한 대역만 어댑터로 (분할 터널). |
| 서버 주소 | 접속한 모든 서버의 IP 에 물리 경로 /32 라우트(bypass)를 자동 추가 → 제어 연결이 자기 어댑터로 빨려 들어가는 루프를 방지. 루프백 주소는 제외. |
| `vpn.bypass` | 항상 물리 네트워크를 쓰는 대역 (예: 사내망, 다른 서버 주소). |
| 마지막 세션 종료 | 어댑터 라우트·DNS·bypass 를 제거(어댑터 자체는 유지) → 다음 핸드셰이크가 항상 물리 네트워크로 들어올 수 있음. 서버 재접속 시 다시 적용. |
| 클라이언트 종료 | 모든 설정 제거 후 어댑터 삭제. |

멀티 서버: 클라이언트는 여러 서버 세션을 받을 수 있으므로, VPN 을 허용한 세션 중 **하나가 활성**이고 나머지는 대기합니다. 활성 세션이 끊기면 다음 세션으로 넘어갑니다(주소가 같으면 OS 설정 변경 없음, 다르면 재적용). 진행 중이던 TCP 연결은 끊깁니다.

## DNS

- 서버 `vpn.dns` 를 비우면(기본) 클라이언트에 **게이트웨이 주소(10.77.0.1)** 를 DNS 로 푸시하고, 서버가 자체 리졸버로 A/AAAA 질의에 답합니다 — 프록시 모드의 `socks5h` 와 같은 "서버 측 이름 해석"입니다. 그 외 레코드 타입은 빈 응답(NODATA)을 돌려주어 클라이언트가 A/AAAA 로 진행하게 합니다.
- 서버 `vpn.dns` 에 공용 DNS(예: `1.1.1.1`)를 지정하면 그 주소를 푸시하고, 질의는 일반 UDP 로 터널을 통해 나갑니다.
- 클라이언트 `vpn.dns` 는 서버가 푸시한 값을 덮어씁니다.
- Linux 는 `resolvectl`(systemd-resolved)이 있으면 어댑터에 DNS 를 설정하고(전체 터널이면 `~.` 도메인으로 우선 사용), 없으면 경고 로그만 남기므로 수동 설정이 필요합니다. Windows 는 어댑터 DNS 를 직접 설정합니다.

## 설정

서버 (`server.yaml`) — 기본값으로 켜져 있으며, 클라이언트가 요청할 때만 세션이 생깁니다.

```yaml
vpn:
  enabled: true            # false 면 VPN 요청 거절
  subnet: "10.77.0.0/24"   # 첫 호스트 = 게이트웨이(서버), 두 번째 = 클라이언트
  mtu: 1500
  dns: []                  # 비우면 게이트웨이 내장 리졸버
allow_private_targets: false  # VPN 출구에도 동일한 SSRF 가드 적용
```

클라이언트 (`config.yaml`) — 기본값은 꺼짐.

```yaml
vpn:
  enabled: true
  interface_name: ""       # 기본: Linux "rproxy0", Windows "AstronLink"
  routes: []               # 비우면 전체 터널. 예: ["10.0.0.0/8", "203.0.113.0/24"]
  bypass: []               # 항상 물리 네트워크로 보낼 대역
  dns: []                  # 서버 푸시 DNS 덮어쓰기
  mtu: 0                   # 0 = 서버 값
```

각 클라이언트 세션은 서버에서 독립된 스택을 가지므로 모든 클라이언트가 같은 `10.77.0.2` 를 받아도 충돌하지 않습니다. 클라이언트 LAN 이 `10.77.0.0/24` 와 겹치면 서버 `vpn.subnet` 을 바꾸십시오.

## 요구 사항

| 측 | 요구 사항 |
|----|-----------|
| Linux 클라이언트 | root 또는 `CAP_NET_ADMIN`, `/dev/net/tun`, iproute2(`ip`). DNS 자동 설정은 `resolvectl` 이 있을 때만. |
| Windows 클라이언트 | **관리자 권한으로 실행**, 실행 파일과 같은 폴더(또는 System32)에 `wintun.dll` (https://www.wintun.net, `install-client.ps1` 이 서명 검증 후 설치). |
| 서버 | 추가 요구 사항 없음 (권한·TUN·NAT 불필요). |

> Windows 트레이 클라이언트를 HKCU Run 키로 자동 시작하면 일반 권한으로 실행되므로 어댑터 생성이 실패합니다. VPN 모드를 쓰려면 관리자 권한으로 실행하십시오(작업 스케줄러의 "가장 높은 수준의 권한으로 실행" 등). 실패 시 로그에 원인과 필요한 조치가 남습니다.

## 보안

- VPN 출구 다이얼은 SOCKS 경로와 **같은 SSRF 가드**를 씁니다. 기본값에서는 루프백/사설/링크로컬/멀티캐스트 주소로 나갈 수 없습니다(`allow_private_targets: true` 로만 허용).
- 가상 서브넷 내부 주소(게이트웨이 제외), 브로드캐스트, 멀티캐스트는 서버 밖으로 나가지 않습니다.
- 게이트웨이에서는 DNS(UDP 53)와 터널 데이터 포트만 응답합니다. 관리 API 등 서버 로컬 서비스는 가상 네트워크로 노출되지 않습니다.
- ICMP: 게이트웨이(10.77.0.1)에 대한 ping 만 응답합니다. 외부 주소 ping 은 서버가 대신 응답하지 않고 버립니다(가짜 도달성 방지).

## 제한 사항

- **TCP-over-TCP**: 패킷이 TLS/TCP 제어 연결 위로 흐르므로, 손실이 큰 회선에서는 내부 TCP 재전송과 겹쳐 처리량이 떨어질 수 있습니다(OpenVPN TCP 모드·SSTP 와 같은 특성).
- 가상 네트워크는 IPv4 만 주소를 할당합니다. IPv6 트래픽은 어댑터로 라우팅되지 않습니다(전체 터널에서도 IPv6 는 물리 경로).
- 외부 주소에 대한 ICMP(ping, traceroute)는 지원하지 않습니다.
- **전체 터널 + 멀티 서버**: VPN 이 이미 활성인 동안 *처음 보는* 서버 IP 가 새로 다이얼해 오면, 그 TCP 응답 패킷이 어댑터로 라우팅되어 접속이 실패할 수 있습니다. 추가 서버 주소는 `vpn.bypass` 에 넣거나 분할 터널(`vpn.routes`)을 쓰십시오. (이미 접속했던 서버 IP 는 bypass 가 유지되어 재접속에 문제가 없습니다.)
- 클라이언트와 서버를 같은 호스트에서 전체 터널로 돌리면 서버의 출구 연결도 어댑터로 라우팅되어 루프가 생깁니다. 같은 호스트 테스트는 분할 터널로 하십시오.
- 킬 스위치는 없습니다. 서버 세션이 모두 끊기면 라우트를 제거하므로 트래픽은 물리 네트워크로 나갑니다(재접속이 물리 네트워크로 들어와야 하기 때문).
